# 卡牌决策知识库：来源、提炼与落地

> 本文是 `spirebrain/cards/` 的**依据文件**。代码里每一个关于"这张牌值不值得拿"的判断，
> 都应该能在这里找到出处；找不到出处的判断，不应该存在于代码里。
> 建档 2026-09-22。

## 0. 一条纪律：版本可信度分级

网上流传的《杀戮尖塔》卡牌清单**大量属于续作（Slay the Spire 2）**，卡名和数值都不一样
（例如 `Crimson Mantle`、`Not Yet`、`Pyre` 在 1 代根本不存在）。用错版本的清单比没有清单更糟，
因为它看起来权威。

因此本项目的规则是：

| 信息类型 | 来源 | 可信度 |
|---|---|---|
| 卡牌数值（费用/类型/稀有度/基础伤害格挡） | **本机 `desktop-1.0.jar`** 的字节码，`tools/extract_card_meta.py` 提取 | 绝对——就是玩家正在跑的那一版 |
| 卡牌效果文本 | 本机 jar 的本地化文件（`gamedata`） | 绝对 |
| 策略结构（分幕优先级、卡组规模、删牌顺序、流派构成） | 社区攻略（下节列明） | 高——多年、多来源相互印证 |
| 具体数值型评级（如"某卡胜率 52.3%"） | 社区数据站 | **未采用**——无法在本机复现，且版本漂移风险高 |

## 1. 来源清单

### 1.1 文字攻略

* **Forgotten Arbiter, *Ironclad Win Streak Guide***（Steam 社区指南，1 代，25+ 连胜纪录者）
  — 防御型铁甲战士的经典框架：卡组要小、删牌先删打击、升级优先级
  `Powers > 功能技能 > 防御技能 > 攻击`、低于 50% 血就休息、Limit Break / Barricade /
  Demon Form 是三大胜利条件但**第一幕不要拿**（除非养得起一张废牌）。
  注：该文写于 2018 年，个别卡片评价随版本变动（如 Feel No Pain），
  所以**只取结构，不取数值**。
* **Jorbs 的"play to the run"原则**（被广泛引用、多来源转述）：
  第一幕要**前置伤害**，第二幕要**续航 + 群伤**并保证打得过精英，
  第三幕只补**当前缺的那一块**（过牌/格挡/虚弱/成长）；
  不要为了想象中的完美卡组放弃眼前这局的信号。
* **spirewiki / stswiki / thegamer / techbloat** 等综合站：铁甲战士三大流派
  （力量成长 / 消耗引擎 / 格挡堆叠）的构成与关键牌，多站一致。
* **爱丁堡大学本科论文《Exploring Different Deck Building Algorithms in Slay the Spire》**
  （2023）——对上述攻略做过系统综述，并提到存在基于万局 A17+ 数据的分幕卡牌强度表。
  本项目把它当作"社区共识确实存在且可复现"的旁证。

### 1.2 视频

无法从视频里抽取可审计的文本，因此**没有从视频取任何具体结论**。列出它们是为了给玩家一个
真人讲解的入口（也是社区公认的学习路径）：

* **Jorbs** — *Overexplained* 系列（逐手讲解决策，教学价值最高，被无数攻略首推）
* **Baalorlord** — 有结构化的铁甲战士专题，如 *Ranking EVERY Ironclad Card*、
  *Ironclad Common Cards: When to Add and Upgrade*
* **TerrenceMHS** — 高难度实战

> 你若让我依据某个视频的具体内容调整规则，请把视频里的**结论**告诉我（哪张牌、什么条件下、
> 为什么），我把它写成可测试的规则，并在这里登记出处。

## 2. 提炼出的规则（已实现，逐条对应代码）

| # | 规则 | 实现位置 |
|---|---|---|
| 1 | 卡组 15–30 张，超过 ~20 张只拿"明显更好"的 | `deck.COMFORTABLE_SIZE` + 规模折扣 |
| 2 | 起手牌的打击/防御**不算真实战力**（社区原话：打击基本等于诅咒） | `deck.profile()` 基础牌 ×0.5 |
| 3 | 一张牌的价值 = 它是否补上卡组当前的短板（伤害/格挡/成长/过牌/能量/群伤/功能） | `deck.grade()` 的 `need_fit` |
| 4 | 已投入的流派要继续加深（核心牌 +0.30，配合牌 +0.18） | `deck._archetype_reasons()` |
| 5 | 协同要**结构化识别**，不是背卡牌对（"有消耗引擎 → 收尾牌更值钱"） | `knowledge._SYNERGY_RULES` |
| 6 | 同一张牌在不同幕价值不同：Demon Form / Barricade / Limit Break 第一幕是废牌 | `knowledge.acts` + `deck.grade()` 的 act 门控 |
| 7 | 陷阱牌要说明**条件**而不是一律禁用（Clash 手里有技能牌就打不出去） | `knowledge.CAUTION` + `_caution_cleared()` |
| 8 | 拿牌不能只看模型：模型弃权时，卡组证据可以拍板 | `decisions.CardRewardJudge._rescued()` |
| 9 | **没有证据就不下结论**：没给卡组、或卡组大半不认识时，本地评估弃权 | `CardRewardJudge._local_grades()` |
| 10 | 每条建议都要能审计（面板显示理由，日志留证据） | `PickGrade.reason_text()` → `detail["reason"]` |

## 3. 三层数据的分工

```
本机游戏 jar ──extract──> data/card_meta.json      事实：费用/类型/稀有度/基础数值/game_id
                                                         │
社区攻略 ──人工撰写──> cards/knowledge.py           判断：能力轴/分幕优先级/流派/协同/陷阱
                                                         │
                        cards/deck.py  ──算术──>        结论：分数 + 中文理由
                                                         │
                        jev_brain/decisions.py ──合成──> 最终建议（模型分 + 本地分 + 门控）
```

分层的好处是**改一层不用重验另外两层**：游戏更新只重跑提取工具；攻略有新共识只改
`knowledge.py`；调权重只动 `deck.py`。`tests/test_cards.py` 里有守卫测试钉住
"手写的卡牌 ID 必须真实存在于本机游戏数据"——这条守卫已经抓到过一次真实 bug
（知识库用游戏 ID `Pommel Strike`，元数据表用类名 `PommelStrike`，两套命名静默对不上）。

## 4. 明确的未完成项

1. **只做了铁甲战士**（75 张）。其他三个角色的卡牌会走 `knowledge.derive()` 的
   文本关键词兜底（标注 `derived`），质量低于人工表。
2. **战斗内出牌决策仍是本地贪心**（`tactical/combat_greedy.py`，约 125 行），
   没有 JEV 参与，也不读本文的分幕规则。
3. **商店买牌 / 篝火升级选哪张** 还没接入卡组评估（升级优先级表已在文档里，未落到代码）。
4. **没有用真实对局数据校准**任何权重：`deck.grade()` 的系数是按文档规则手工设定的，
   等 `logs/advice.jsonl` 积累到足够样本后，应该用真实采纳/胜率数据回归一遍。
